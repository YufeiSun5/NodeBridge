## 1. 目标与边界

验证真实 MySQL -> Canal -> RabbitMQ -> Apply -> MySQL 链路，重点检查：

1. FB-052 优化在持续写入、日志增长和 50 列 payload 下能否稳定推进。
2. INSERT、真实 UPDATE、DELETE/软删除、再插入、表列映射、ADD/DROP 的正确性。
3. FB-054 的同批重复事件、跨批重放、更新后重放旧事件不会卡队列或恢复旧值。
4. 双端 Agent 停机期间继续写源库，恢复后积压可排空，无丢失、无回环。

运行环境：Server `192.168.10.103/scada_center`，Edge `192.168.10.105/scada_edge`。两端当前临时运行与最终交付包一致的v0.46.8 SyncAgent；结束恢复原路径，未永久覆盖边缘安装目录。

默认 `crud_ordered`，全局 compact 关闭。compact 的双开关与重复边界保留独立 smoke/单元测试，不把 compact 吞吐混入本轮保序验收。

不声称覆盖 broker 自动重连：当前 AMQP 连接丢失仍可能需要重启 Agent。本轮正式故障为 Agent 停机，不修改防火墙、不切断 SSH、不重启共享 MySQL/RabbitMQ/Canal。网络断线和 broker 崩溃另立带恢复授权的专项。

## 2. 五十列模型

机器可读母本：`scripts/fixtures/longtest-wide50.schema.json`。每张主测试源/目标表均为 **50 列**，InnoDB、utf8mb4；开始前查询 `information_schema.columns` 逐表断言，不只检查定义文件。

| 序号 | 列 | 类型与用途 | 数量 |
| --- | --- | --- | ---: |
| 1-12 | `id/run_id/seq_no/revision/sync_version/updated_by_node/last_event_id/created_at/updated_at/is_deleted/deleted_at/deleted_by_node` | 主键、测试归属、顺序版本及回环/删除元数据 | 12 |
| 13-24 | `i01` 至 `i12` | BIGINT，可空，正负整数与计数 | 12 |
| 25-36 | `n01` 至 `n12` | DECIMAL(18,6)，可空，精确小数 | 12 |
| 37-46 | `t01` 至 `t10` | VARCHAR(128)，可空，中英日及转义字符 | 10 |
| 47-50 | `flag_value/counter_value/payload_text/optional_text` | TINYINT、BIGINT、TEXT、可空 VARCHAR(512) | 4 |

`id`、`run_id`、`created_at` 等身份列保持稳定，不为了凑更新列数修改主键。38 个普通业务字段必须被实际填充，且在整个 UPDATE 场景中均有修改覆盖，不使用 38 列全部默认值的空壳宽表。所有 50 列都必须有明确的比对或元数据校验规则。

数据由固定 seed、主键、revision 和列序号确定，可重建预期结果。NULL、空字符串和零分别编码；DECIMAL 用十进制定点字符串处理，禁止先转二进制浮点再比较。时间统一到毫秒，连接时区固定 UTC。普通主键范围限制在整数精确传输范围内；BIGINT 精度边界另外放入启动 smoke，失败不得忽略。

普通 TEXT 约 256 字节，少量 4 KiB/8 KiB 样本；VARCHAR 覆盖空值、接近长度上限、中英日、引号和换行。生成器记录实际平均/P95 行字节数，不能用旧 128 字节 payload 基准代替宽表吞吐结论。

## 3. 表与规则

每次使用唯一短 run-id，物理表名形如 `nb7_<run>_e_stream`，严格校验标识符且不超过 64 字符。禁止复用旧 overnight 表或删库重建。

| 逻辑表 | 方向 | 模式 | 映射 |
| --- | --- | --- | --- |
| Edge stream -> Server archive | EDGE_TO_SERVER | append_only | 源/目标表不同，`id -> record_id`、`seq_no -> source_seq` |
| Server stream -> Edge inbox | SERVER_TO_EDGE | append_only | 源/目标表不同，`id -> record_id`、`n01 -> value01` |
| Edge state <-> Server settings | BIDIRECTIONAL | crud_ordered | `id <-> setting_id`、`t01 <-> label01`、`n01 <-> value01`，反向规则明确逆映射 |

三对逻辑表共六张物理表，全部 50 列。状态表先准备两组各 1,000 个活动主键，由 Edge/Server 分区写入；不同主键双端持续写，同一主键的交替写使用明确同步屏障，不把未定义的并发冲突混入保序判定。

所有规则按 `source_node_ids` 限定来源，禁止回发 origin。主表全字段映射；列排除/禁止结构变更另用独立 50 列 guard 表做少量探针，不污染主流的全字段一致性结论。

## 4. 必须是真实 UPDATE

初始化用 INSERT，此后状态负载使用参数化 SQL `UPDATE ... WHERE id=?`，禁止用 `INSERT ... ON DUPLICATE KEY UPDATE` 代替全部更新。每次 revision 增加，必须断言实际影响一行；更新到不存在的行按夹具失败处理。

- 50%：轮换 1-3 个业务列，验证未修改列不被清空。
- 25%：一次修改全部 38 个普通业务列，保留主键/归属/创建时间。
- 15%：NULL -> 非 NULL -> NULL、空串 -> 文本、零 -> 负数等往返变化。
- 10%：热点主键连续递增 revision，多次更新不能回退；最后一版必须收敛。

同时更新 `revision/sync_version/updated_at/updated_by_node`，清除本地业务更新携带的旧 `last_event_id`，遵循现有回环判定约定。各分支使用独立计数器，不用总 INSERT 轮次的奇偶触发，以免漏掉分支。

每 5 分钟执行小规模 `INSERT -> UPDATE x3 -> DELETE -> 等待目标 tombstone -> 再 INSERT`。源物理删除与目标软删除按预期模型比较，不要求它们最终物理行数相同。删除、再插入各有独立断言与日志，不只看最终行还在。

## 5. 七小时安排

安装、预检与至少 10 分钟的宽表 smoke 在计时前完成。正式时钟共 420 分钟；最后 30 分钟包含排空、核验和恢复。超时按失败结束，不静默延长为八小时或降低负载后仍报通过。

下表速率为**每个方向**的目标行事件/秒，INSERT 与 UPDATE 各自计数。两个持续生产器独立运行，不因快照、故障等待或另一方向阻塞而一起停写。

| 正式时间 | INSERT/s | UPDATE/s | 场景与门禁 |
| --- | ---: | ---: | --- |
| 00:00-00:30 | 20 | 10 | 稳态基线、单条端到端延迟、50 列覆盖 |
| 00:30-02:00 | 40 | 20 | 持续双向混合负载，每 5 分钟 CRUD 生命周期 |
| 02:00-02:15 | 40 | 20 | 仅停 Edge Agent 15 分钟；两端源库继续写 |
| 02:15-03:00 | 40 | 20 | 恢复 Edge；要求 30 分钟内追平，再保持稳态 |
| 03:00-03:15 | 40 | 20 | 仅停 Server Agent 15 分钟；两端源库继续写 |
| 03:15-04:00 | 40 | 20 | 恢复 Server；要求 30 分钟内追平，再保持稳态 |
| 04:00-04:30 | 20 | 20 | 双向 ADD/DROP、列映射和 guard 拒绝/排除探针 |
| 04:30-05:00 | 80 | 40 | 宽表短时峰值，不使用 compact |
| 05:00-05:30 | 20 | 60 | 更新占主导、热点交替写、同批/跨批重复与旧事件重放 |
| 05:30-06:30 | 40 | 20 | 故障后稳态与历史日志增长观察 |
| 06:30-07:00 | 0 | 0 | 停生产、排空、全量核验、恢复原规则和 Agent |

理想按时提交时，每方向约 **900,000 条 INSERT + 558,000 条 UPDATE**，双向合计约 **2,916,000 条业务事件**；另加预置状态行、少量 DELETE/DDL/重复探针。以生成器成功提交账本为最终分母，不能用计划数冒充实写数。

生产器不在每轮 SQL 完成后额外固定 sleep 一秒；用单调时钟安排目标 tick，记录欠账和实际提交速率。非故障阶段持续 5 分钟低于目标 90% 即失败/负载未达标，不自动降档。峰值可以产生积压，但必须记录峰值及恢复时间，并在最终门禁前排空。

## 6. 结构与幂等探针

ADD/DROP 在专用受控列上运行：50 -> 51 -> 50 列，不删除 50 列母本内的业务数据。两方向分别授权，非 SERVER_TO_EDGE 的 DROP 恰好指定一个来源节点。先等待 ADD 真正到达，再写新列；DROP 后等待列消失再继续后续步骤。

重复事件探针显式保证落入同一批次：暂停对应测试消费者、向专用测试队列/已隔离测试路径发布同一稳定 event_id 四次，再启动批量消费。不得仅在消费者运行时连续发两次就声称覆盖同批重放。

验证新 INSERT 的四个副本，再次重放四个副本，以及 `U1 -> U2 -> 重放 U1`。每个唯一事件只有一条 apply log；业务行只有一份，最后值是 U2。重复消息全部处理完后队列为空，重复投递数单独计数，不冒充新业务事件数。

不同 event_id 但同业务主键的 append-only 冲突必须报错，不可通过 INSERT IGNORE 吞掉。此负向探针使用独立 queue/table，按事件 ID 留证并定点恢复，不阻塞主长测队列，不执行全队列 purge。

## 7. 观测与正确性

- 每 15 秒采集生产账本、源/目标高水位、ready/unacked、消费者数、失败/retry/dead 数、Agent PID/心跳。
- 每分钟采集两端进程 CPU/RSS、磁盘空闲/IO、MySQL 业务表和三类系统日志增长；每 5 分钟生成窗口速率和延迟分位数。
- 吞吐同时看源提交、Canal 读取/提交、Server 分发 SUCCESS 和目标 apply。队列为空不代表 Canal 前没有积压。
- 日志按唯一物理测试表、run-id、主键范围和事件身份关联，只统计本次数据；旧失败记录不当作新错误，计划内负向探针单独列账。

一致性分三层：

1. **在线**：已闭合的 append 分片核对行数和高水位；状态抽样对照生成器的已确认版本，允许正在传播的有界滞后。
2. **停止生产后**：按主键排序、分块读取全部业务行，经逆映射与类型标准化逐列比较。对每块计算 SHA-256 并定位不一致的主键/列；不用 `SUM(CRC32(...))` 单独作为完整性证据。
3. **系统语义**：唯一 event_id 的 apply log 无重复；需要 SUCCESS 的事件最终成功；回放元数据按现有代码约定校验，源/目标可不同的 `last_event_id` 不做盲目字节相等。软删除与已移除源行使用操作账本生成预期 tombstone 集合。

序列化使用稳定列顺序、类型标识、NULL 标识和长度前缀，区分 NULL/空串/零，避免直接 `CONCAT_WS` 跳过 NULL 造成漏检。BIGINT 用十进制文本或整型，DECIMAL 不转 float。对 50 列定义覆盖报告：字段填充值、更新次数、NULL 往返次数、最终比较数量。

`revision` 只能前进；热点探针采集版本观察序列和事件日志，防止“最终值正确但中途回退”被忽略。源业务提交账本先在同一源事务中持久记录，再由控制器收集，避免控制器在 COMMIT 后崩溃而少记分母；账本表不参加同步。

## 8. 启动与停止门禁

启动前全部满足：

- 两端安装包/运行二进制 hash 一致；配置、规则、运行路径已备份并记录。用户确认本次启动后才运行，不创建定时任务。
- 新宽表编排器先完成测试和10分钟smoke；确认真实UPDATE、50列及全部语义门禁。v0.46.8的160102已通过，旧overnight脚本不作为本方案执行器。
- 原队列无未解释积压；MySQL binlog/Canal filter 能捕获新 run 表；节点来源、反向映射、soft-delete 和 DDL 权限预检通过。
- 预检实测日志与 binlog 放大量。每台数据盘空闲至少 `max(40 GiB, 预计剩余增长 x 1.5 + 10 GiB)`；预估不足直接阻止启动，不能把业务表大小当作全部占用。
- 一次只运行一个实验室长测，独立 supervisor/heartbeat 看守，不修改系统睡眠策略或共享组件配置。

异常处理：

- 非计划退出、生成器心跳超时、源提交失败、错误/死信新增、连续无进展超过 5 分钟或任一校验不一致：停止新增负载、保存快照、按 manifest 恢复现场并判失败。
- 故障恢复 30 分钟未追平：失败；不因“还在增长”无限等待。磁盘低于 10 GiB 或未来 15 分钟预计耗尽则受控停止。
- 不以通用 `Stop-Process SyncAgent` 停进程；按已记录路径/PID/启动时间定位，优先 stop-file。SSH 保持可用。
- 无论成功失败，都恢复原规则和原 Agent 路径，核对规则 hash；保留测试表、事件、账本和日志作为证据。残留消息只按本 run 身份处理，不清空共享队列。
