## FB-058：JSON 数字精度

使用包内真实 `consume-batch-once`，在独立队列、独立 50 列目标表发布 JSON 数字事件，字段 `i01=9007199254740993` 被写成 `9007199254740992`。消费者仍返回 `action=applied`。队列无其他消费者，消息在发布确认后才启动批量消费。

`internal/syncruntime/runtime.go` 多个消费/重放入口直接 `json.Unmarshal` 到带 `map[string]any` 的事件结构，JSON 数字因此进入 `float64`。修复需要统一无损解码，并覆盖所有入口；只改一处消费代码不足。

**范围限定**：Canal 的 `columnValue` 当前返回字符串。本次边界失败证明 JSON 数字事件入口存在问题，不证明 Canal 字符串形式的大整数同样丢精度。Canal 边界仍需单独复测。

## FB-059：真实双向版本回退

两个生产器按不同主键分区写入，源事务在写业务 UPDATE 的同一事务中保存 oracle。停载后，Edge/Server 自有热点行都低于已提交的最终版本，且生命周期再插入行也未收敛。

中心对本轮 Edge 状态表记录了 **24,308 条 UPDATE apply**，而 Edge 主生产 UPDATE 仅 5,730，另只有少量生命周期操作。主键映射后的版本回退与更新放大同时出现，不能用零错误日志或流水行数一致排除问题。

当前根因线索：`internal/apply/worker.go` 的 INSERT/UPDATE 直接写映射后的行，没有把本次事件 ID 写入 `last_event_id`；`internal/loop/suppressor.go` 只在该字段非空且命中 apply log 时识别回放。该 run 自写热点的 `last_event_id` 为空，回传旧行像新业务变更一样进入后续链路。最终因果与修复由 backend-ai 复核，需覆盖元数据、回环、同键顺序与再插入，而非简单丢弃旧版本。
