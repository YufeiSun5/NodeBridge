# v0.46.11 回放判定与位点写入修复

日期：2026-09-10。backend-ai实现，test-ai负责实装与真实准入。对应FB-073、075、076、077、078。

## 故障依据

`widesmoke_0909_234447`完整生成每端64220 INSERT、39850 UPDATE，但最终Server来源UPDATE账本期望39888、实际39889。多出事件携带Edge回放标记，并能找到对应Apply记录。旧`Store.Exists`使用普通查询，且把SQL错误当成不存在。

隔离MySQL实验确认：普通查询在未提交Apply记录前返回0；事务内`FOR SHARE`读等待写事务提交后返回1，回滚后返回0。这支持提交可见性竞态解释，但不等于对原故障瞬间的直接SQL时序证明。

## 修复边界

- `ApplyLog.Exists`及上传判定接收context并返回error。缺失依赖、查询失败、提交失败或取消均阻止发布；Canal不得ACK该批次，由已有重置流程重试。
- Store在显式事务中使用`SELECT 1 ... FOR SHARE`，等待Apply事务结果，避免把尚未可见的回放记录误判为本地业务。
- 运行时`Offset.SkipCheckpoint`不序列化。空批次和全部抑制批次仍ACK，但不写SQL位点，避免位点写入产生新的CDC空批次并持续自写。有效业务即便没有活动Edge仍保存位点。
- 测试监督器最终验收重试改为一致的DateTimeOffset比较，覆盖跨午夜、时区、期限边界；不修改精确账本或延迟门禁。
- 不变更SyncEvent、Wails API/DTO、UI、配置项、同步表映射及RabbitMQ业务提交后ACK不变量。
