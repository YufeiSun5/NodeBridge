## 判断

业务 AI 的报告总体合理，且清楚区分安装版链路、源码模拟、SQL语义与人工恢复。NB-01至08可在对应源码中核实，不能归因于业务方误用。单向汇总、独立目标库、由业务系统准备schema、暂不混合旧宽表、按唯一键设计多节点归属均合理。

需要限制的结论：source_node_ids仅路由，不提供数据库键隔离；连接成功不代表写权限齐全；失败列表空/队列空不代表一致；人工补行与清理不算同步能力。仅补回环列不能安全启用双向。append_only拒绝变更是设计边界。报告没有要求通用授权/数据库管理平台，本轮撤销误加的MCP范围授权与审批体系，MCP启用后全部现有工具开放。

## Q1至Q12答复

| --- | --- |
| Q1 删除版本/字段 | 源码已有 delete_mode HARD/SOFT，尚无已发布版本。新建UI显式HARD；旧缺省SOFT，读取不写文件，显式保存补出SOFT。没有静默转物理删除。 |
| Q2 字段要求 | 单向HARD使用完整映射键DELETE，不加软删字段；源软删UPDATE仍为UPDATE。SOFT结构/类型预检尚未完成，缺列仍会在执行时报错，不宣称已满足启用前预检。 |
| Q3 缺行/历史账本 | 新UPDATE缺行返回target_row_missing，不记成功；同值更新成功。修复数据后同事件可以重试。历史已经误记成功的event_id仍会幂等跳过，不能靠原事件重放修复，不能删除内部账本；受控历史对账修复功能待实现。 |
| Q4 唯一键 | 普通INSERT改严格INSERT，1062返回unique_key_conflict并保留MySQL错误链，不改已有主键。同event_id为幂等；不同event_id同PK也报冲突。未提供可配置UPSERT或完整结构化冲突双方PK详情。 |
| Q5 冲突裁决 | 未实现SERVER_WIN/LAST_WRITE_WIN，当前源码拒绝启用；旧安装版不能当作生效。只支持NONE单写者。 |
| Q6 双向 | 当前源码拒绝启用BIDIRECTIONAL。回放标记保留导致合法本地编辑被抑制的问题没有用加列假装修复；物理删除回环与旧事件复活未验收。 |
| Q7 首次对齐 | 只有DISABLED/MANUAL选项和能力声明，执行/在线衔接均不支持。没有可调用的对齐执行工具；目标额外行不能由HARD隐式删除。 |
| Q8 规则预检/跨库 | 连接测试不执行目标DML权限检查，所以不能发现1142。按规则跨库schema/权限预检仍待实现；本轮未扩大任意SQL，也未改业务连接指向。 |
| Q9 失败事件范围 | failed_events读取sync_ack_log的FAILED记录，不覆盖所有入站Apply即时重试。当前须结合运行错误日志及apply账本核查；统一retrying/event_id/rule_id/位置/下次重试查询未完成。空列表不是健康证明。 |
| Q10 保存/生效/CAS | 保存仍替换规则数组，无expected_revision，运行中规则未提供active_revision证明。不得据保存成功宣称已热生效；协调单写者，重启属于用户的现场操作，本轮不执行。 |
| Q11 多节点键 | source_node_ids只选择规则，不自动增添复合PK/唯一键维度；需业务方保证各唯一约束的跨节点隔离，或使用不同目标表/库。 |
| Q12 残留事件 | 本轮未接触残留。当前禁用/不匹配规则可能跳过并ACK，因此不能带着禁用规则直接启动并把队列下降当恢复。应先保留原消息证据，准备按事件审计处置方案；尚未交付新的隔离/重放工具，不清整个队列。 |
