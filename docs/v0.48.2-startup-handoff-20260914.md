## 修复的行为

- 单向规则只检查其实际读写的本地物理表。无关禁用表的失败首次对齐作业及 PENDING 组不再阻断启动；同表未完成作业仍阻断，不能靠改规则 ID 或方向绕过，也不删除历史账本。表名匹配使用 MySQL 大小写模式。
- ACTIVE 复制释放 `scope_hash` 预约后，仍按持久计划的本端表归属加载证明。
- 本机启用双向规则时保留同一中央表的完整拓扑映射，包括其他边缘成员的异名表列。此前只按本机规则 ID 裁剪导致三节点启动报 `alignment_topology_manifest_incomplete`；现在保持完整组并继续核对持久 ACTIVE 证明。
- UI/MCP 启动等待对应 PID 的 ready 标记及短暂稳定。提前退出或超时返回 `ok=false`、`error` 和本次启动日志，不再把创建进程视作启动成功。状态可为 `starting`；`running` 不代表全链路持续健康或业务同步验收通过。无新增方法、DTO 字段或用户参数。

## 业务 AI 接续

1. 各参与节点切换到上表哈希对应的 0.48.2。便携 ZIP 包含 Agent 与完整系统迁移，可解压到独立目录；更新 MCP 实际程序路径并重开 stdio 会话。已运行的旧进程不会自动更新。
2. 保留原连接、规则、首次对齐账本及配置所属 Windows 账户。DPAPI 密文不可跨机器/账户搬运。若覆盖安装，先停止同步并显式退出旧 UI。
3. 若已完成 0.48.1 的迁移 010，本版没有新增迁移。更早版本应先核对配置指向 NodeBridge 系统库，再按本机角色执行完整迁移：

```powershell
SyncAgent.exe migrate -config <existing-config.yaml> -scope server
SyncAgent.exe migrate -config <existing-config.yaml> -scope edge
```

每台只选符合自身角色的一条；`migrations` 目录须与程序同级。不要给业务表加同步列、删对齐作业或清空回放证据。

4. 沿原业务授权恢复目标单向规则并启动，检查启动返回、对应 PID 持续存活、实际 INSERT/UPDATE/DELETE 及两端结果。若仍报同表 PENDING，应走既有首次对齐状态/恢复流程，不能删除账本解锁。
5. 双向沿用 0.48.1 系统事务标记要求：Canal 过滤必须包含系统表 `sync_capture_fence`、`sync_replay_marker`。本版本不要求或覆盖业务 `last_event_id`、`updated_by_node`。
