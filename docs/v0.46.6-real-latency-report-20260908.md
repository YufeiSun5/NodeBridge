# NodeBridge v0.46.6 真实内网延迟报告

日期：2026-09-08

## 结论

真实 `192.168.10.105 Edge -> 192.168.10.103 Server` 链路的单行端到端延迟已从 v0.46.5 的 `5.13-11.44s` 降至：

| 指标 | v0.46.6 最终值 |
| --- | ---: |
| 样本数 | 20 |
| 最小值 | 62.569ms |
| P50 | 79.745ms |
| P95 | 141.854ms |
| 最大值 | 142.122ms |
| 平均值 | 91.896ms |

20 条探针均在写入前保持 1200ms 空闲间隔，避免批量流量掩盖空闲唤醒延迟。最终源表、目标表、`sync_apply_log` 和 SUCCESS `sync_event_log` 均精确为 20，所有相关队列为 0，失败 ACK、近期中心错误和边缘失败事件均为 0。

## 根因与修复

1. `workerConfig` 错误地将 `sync.retry_interval_seconds=10` 同时用于正常空闲轮询和错误退避。Edge CDC、Edge upload 与 Server ingress 可连续叠加 10 秒等待。v0.46.6 将正常空闲轮询固定为 100ms，错误退避仍遵守原配置。
2. Canal 客户端空闲长轮询为 1000ms。中心收到事件后实际只需 1-4ms 完成事务应用，剩余约 0.8 秒发生在中心接收前。v0.46.6 将 Canal 长轮询收紧为 100ms。

仅修复 Worker 空闲轮询后，真实 20 条样本为 `p50 807.462ms / p95 840.521ms / max 843.931ms`；正式二进制在保留该修复并收紧 Canal 长轮询后得到最终约 92ms 平均值，验证了两个等待点的独立影响。

## 测量方法

- Edge：`192.168.10.105`，MySQL 8.4，节点 `edge-001`。
- Server：`192.168.10.103`，Docker MySQL 8.0.38 与 RabbitMQ。
- 路径：`MySQL -> Canal -> Edge RabbitMQ -> Server RabbitMQ -> Apply -> MySQL`。
- 写入端使用持久 SSH/MySQL 会话，读取端使用持久 Docker/MySQL 会话。
- 计时从发送单行 INSERT 开始，到中心表首次查询可见结束；查询间隔 10ms。
- 可复现命令：`scripts/lab-real-latency-e2e.ps1 -Count 20 -IdleBetweenProbesMillis 1200`。
