- 108 没有复制作业，但有一个 PENDING 拓扑意图。这是另一个需要处理的持久状态，不能只看 job 表为空。
- 原始本地证据在 `output/status-nodebridge*.json`。不将环境配置或业务内容放进公开文档。

## 本轮代码修正

1. 受管边缘账号权限模板补齐对齐使用的 session/offer/frames/replies 队列的 configure/read，以及默认交换机 `amq.default` 的 write。普通上下行权限保留并加完整名称锚点。
2. 对齐双方交换状态后、进入会写入拓扑意图的 BeforePlan 前，检查旧计划规则哈希。冲突返回明确的旧/新映射、作业和计划 ID，不再先留下新的 PENDING 意图才报笼统错误。
3. 不改变业务数据、旧作业 phase、旧证明、版本或墓碑。名称修改仍与规则语义分离；双方尚未完成的取消仍阻断。

RabbitMQ 当前协议通过默认交换机发布，write 权限不能按 routing key 限定到某个边缘的队列；对齐队列也使用共享哈希命名空间。因此这次修复不宣称实现多租户消息隔离，不将所有 vhost 资源授予 `.*`。若要实现恶意边缘之间的隔离，需要独立 vhost 或带节点命名空间的专用交换机协议。

## 早期缺口（实现状态已由 0.48.8 交付报告覆盖）

早期版本没有安全迁移/重建基线入口。0.48.8 已增加预览与准备 MCP 流程；普通旧对齐重试仍不能代替迁移。

仅把旧 job 标为 CANCELLED、忽略 RuleHash 或移走 pairs 文件都不成立：

- 105 已有行版本历史。若涉及所迁移的物理表，重新首次复制仍会被 `alignment_existing_conflict_history` 拦截；本轮只读查询尚未逐表统计。
- 已有墓碑与修复任务不能丢失，旧消息 epoch 不能当成新一代事件接收。
- 108 的既有数据不能由普通首次对齐覆盖；当前协议明确拒绝两端非空。
- 部分节点成功、另一端断线的情况下，不能让任何一端提前启动同步。

以 105 为准的迁移需要一个明确的“重建基线”协议：

1. 预览所有受影响规则、完整拓扑成员、系统历史、队列及业务表约束，固定配置和规则 revision。
2. 两端停止同步并持有维护锁；明确目标端业务写入的维护窗口，验证 108 数据和两端系统历史的可恢复备份。
3. 持久记录迁移计划、权威源、旧证明到新证明的关联及执行阶段；旧历史可审计，不能以删账本代替迁移。
4. 在事务保护下按 105 快照重建目标基线，协调新的 CDC 边界；明确处理旧 epoch 的版本/墓碑和积压，不能只复制可见业务行。
5. 双方收据齐全后才启用完整新拓扑；失败须能断点核对，提交结果未知时不能盲目重做。
6. 隔离环境验证迁移、断流、重启、重复执行、旧消息重放、非空目标和备份恢复，再出包进行现场验收。
